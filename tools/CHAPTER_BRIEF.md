# 解説 1章を書くための共通の指示（作成エージェント向け）

学習アプリ「Claudeまなび帳」（Claude アプリと Claude Code の機能を学ぶ、非公式の学習 PWA）の解説を1章分と、その章の確認クイズ・用語を作る。リポジトリ：このリポジトリの直下。

## 先に読むもの

1. `CONTENT.md` の 2〜6・8・9 節（データ形式、図の書き方、情報源と文章のルール）
2. 作業ファイル `work/<章id>-brief.md`（節の案、最初に読む公式ページ、既存の用語、ほかの章の節）
3. 公式ページ。brief の URL から始め、必要なら同じサイト内のリンク先も読む。Claude Code のページは `https://code.claude.com/docs/en/<ページ>.md` で本文が取れる。ヘルプセンターは `https://support.claude.com/en/articles/...`

## 内容の方針

- **公式情報で確かめたことだけを書く**。記憶や推測で補わない。公式の記述どうしが食い違うとき、表記が確認できないときは、書かないか、その節を `unverified` にして報告に挙げる
- **転載しない**。公式の文章・構成・例を言い換えて並べるのではなく、初めて使う人に向けて「何のための機能か → どう使うか → 注意点」の順でオリジナルに書く。例（指示の文例、フォルダ名、題材）は自分で考える。公式の図は写さない
- **変わりやすい数値を書かない**：料金、利用上限、ファイルサイズや個数の上限、プランごとの提供条件、「◯日以内」などの期限。必要なら「プランによって異なります」と書き、`sources` のページで案内する
- 提供状況：公式に beta／research preview などとある機能は、その節の `status` を `beta`／`preview` にする。節の中で一部だけがベータなら本文で触れ、`status` は節の中心の機能に合わせる
- 使える場所（`surfaces`）：公式に書かれている場所だけを入れる。「どこで使っても同じ」のような一般的な記述だけを根拠に広げない（例：CLI のスラッシュコマンドがデスクトップや IDE で使えるかは、そのページに書かれているときだけ入れる）
- 過去の検査で多かった指摘：公式の表（Include／Exclude など）や例（コマンド名・数値・文例）を訳して並べた形になっている。表や例は、架空の小さなプロジェクトや題材を自分で決めて作り直す
- 画面の操作手順は、メニュー名などが公式に書かれている範囲で書く。日本語 UI の表記が確認できない名前は英語のまま（例：「Project knowledge」）とし、訳語を推測で作らない。UI の細部は変わりやすいので、手順は「どこで何をするか」の粒度にとどめる
- 製品名・機能名は公式の英語表記に合わせ、初出で日本語の説明を添える
- 「やってみよう」に関わる操作は、練習用のフォルダやリポジトリで行う前提で書く。本番リポジトリの削除、強制 push、API キーなどの秘密情報を扱う操作を例にしない
- 文体は「です・ます」調。1文を短く

## 分量と構成

- 1章 10〜15分で読める量：本文（`text`・`items`・`answer`・`code`）で 5,000〜7,500字。節は 4〜8、1節 600〜1,200字
- 各節：`points`（2〜4個）、`digest`（書き下ろしのまとめ 200〜400字＋`keys` 3〜6個。本文にない事実を足さない）、`blocks`
- 図：章全体で3つ以上。`chat`（チャット画面の簡略図）、`terminal`（ターミナルの表示例）、`dir`（フォルダ構成）、`layers`（優先順位・階層）、`flow`（流れ）、`seq`（並び・内訳）から内容に合うものを選ぶ。実際の画面や出力をそのまま写さず、要点だけの簡略図にする
- 図はスマホの縦画面（幅 約340px）に収まるようにする：箱の文字は全角10字程度まで、`flow` の分岐は左右1列ずつ（col は -1・0・1）まで、`seq` の1行は4〜5マスまで。長い説明は本文に書く。図の中（caption を含む）では `[[ ]]` を使わない
- コマンド・設定例・指示の文例は `code` ブロック（コピーボタンが付く）。`lang` を付ける
- 注意書き：`note` の `kind` は `tip`（コツ）／`pitfall`（つまずきやすい点）／`caution`（安全・データ・権限に関わる注意）
- `minutes` は本文の字数 ÷ 500 を切り上げた値
- 各節の `sources` には、その節の根拠にしたページだけを1〜4件。`title` はページの題名（日本語版があれば日本語版の題名と URL）。`checkedAt` は今日の日付。`verification` は `{ "status": "unverified", "note": "" }`（検査後に別の担当が更新する）。`tryIds`・`dictIds` は空配列

## クイズ（`work/<章id>-quiz.json`）

- CONTENT.md の 6 節の形式。1節あたり2〜3問
- 仕組み・使い分け・手順・目的を問う。「〜はできない」「〜にしか対応していない」のような、仕様変更ですぐ誤りになる問いは避ける。料金・上限・プランの条件は問わない
- 誤りの選択肢は、もっともらしいが本文と公式情報に照らして明確に誤りであるものにする。正解の位置（0〜3）は章の中でばらつかせ、正解の選択肢だけが長くならないようにする
- `explanation` は、正解の理由と、紛らわしい誤りの選択肢がなぜ違うか（2〜4文）。`sources` は根拠のページ

## 用語（`work/<章id>-terms.json`）

- `{ "terms": [ … ] }`。CONTENT.md の 5 節の形式。この章の理解に必要で、用語集にまだない語を 5〜12 語
- brief の「用語集にすでにある用語」と同じ語は追加しない。一般的すぎる語（ファイル、設定など）は入れない
- 本文では用語集と同じ表記で書く（自動でリンクされる）。表記が揺れる語は `aliases` に入れる

## 自己検査

書き終えたら、リポジトリ直下で次を実行し、エラーがなくなるまで直す。警告（料金らしい表現など）も確認し、本当に料金・上限の記述なら削る。

```
node tools/check-draft.mjs <章id>
```

一時ファイルが必要なら `work/<章id>-draft-` で始まる名前にする。`work/` 以外のファイルは変更しない。
